# TraceTriage for Android

Three screens over the same measurements the console shows, and the same endpoint it measures
with. There is no mobile backend and no mobile copy of the data: the app reads
`/data/queue.json`, `/data/cards.json` and `/data/provenance.json` from the deployment and
posts to `/api/live/`, so a number on a phone and the same number on the web cannot disagree.

| Screen | What it does |
|---|---|
| **Queue** | The 407 ranked passes, highest review value first, with the reason codes verbatim from `artifacts/QUEUE_RECEIPT.json` |
| **Pass** | The fitted Doppler corridor drawn over the waterfall it was fitted to, with the offset in Hz and ppm |
| **Live** | Post any SatNOGS observation id and the endpoint downloads that waterfall and fits a corridor to it while you wait |

The Pass screen is the one worth opening. A list of scores is a list of scores; the question a
reviewer has is whether the corridor sits on the trace, and that is a picture.

## Install

Download `tracetriage.apk` from the [latest release](../../releases/latest) and open it.
Android will ask you to allow installing from this source, because this is not a Play Store
listing. Minimum Android 7.0.

Check what you downloaded before you trust it:

```
sha256sum tracetriage.apk                       # compare with the release notes
apksigner verify --print-certs tracetriage.apk  # compare with the fingerprint below
```

Signing key SHA-256:

```
98:B5:30:88:7C:39:6B:D9:78:0B:1F:48:71:54:61:3D:B3:B6:B5:76:17:94:D7:B7:37:83:4A:9C:0B:A1:A8:0D
```

That fingerprint is the public half of a 4096-bit RSA key held outside this repository. It is
published so a download can be checked, and pinned in `build-apk.ps1` so a build signed by
anything else fails before it can be released rather than after.

There is no iOS build. It needs a paid Apple Developer account, and a submission with a dead
TestFlight link in it is worse than one with no iOS row. The console is an installable PWA
instead: on iOS Safari, Share then Add to Home Screen, and the eight pages work with no
network after the first load. That is measured, in `artifacts/OFFLINE_RECEIPT.json`.

## Build it yourself

```
npm install
npx expo prebuild --platform android
powershell -ExecutionPolicy Bypass -File build-apk.ps1
```

`android/` is generated by the second command and is not tracked, so the release signing
config lives in `plugins/with-release-signing.js` rather than in the generated file: a
hand-edited `build.gradle` survives until the next prebuild and then silently reverts to the
public debug key. With no keystore present the build still works and produces a debug-signed
APK, which is what a fork needs; `build-apk.ps1` then says so rather than letting it pass as a
release.

Two things that will waste an afternoon otherwise:

- **`JAVA_HOME` must be a JDK between 17 and 21.** Android Studio ships one at
  `<install>/jbr`, which is what `build-apk.ps1` uses. A system Java 22 fails with an
  unsupported class file version, which reads like a corrupt dependency.
- **`apksigner` is per build-tools version.** The script picks the newest one that has it,
  because an SDK accumulates several and the oldest is usually the one on `PATH`.

## What is checked, and where

`tests/test_mobile_client.py` in the repository root pins the properties that make this the
same product as the console rather than a lookalike: the nine palette values against
`apps/web/app/globals.css`, the origin against the console's own `metadataBase`, the trailing
slash on `/api/live/`, that all three screens are reachable, and that the signing plugin is
still registered. `npx tsc --noEmit` covers the rest.
